# 0023: GIF through the canvas-decoder seam

- **Status:** Accepted (T5.2)
- **Date:** 2026-11-11

## Context

T5.2 plays GIF through the same YUVA cache path as animated WebP ([ADR 0022](0022-animated-webp.md)): a `CanvasDecoder` that composites a straight-alpha RGBA canvas per frame, converted by `RgbaToYuva`. giflib 6.1.3 (decoder only) was already pinned and built. GIF files are attacker-controlled, and giflib's high-level reader (`DGifSlurp`) would read every frame's pixels into memory, so the design is mostly about how to read it safely and which policies to pick where browsers and the spec differ or are silent.

## Decision

1. **Reading.** Never `DGifSlurp`. `GifStream` (`src/demux/gif.*`) opens giflib over a bounds-checked in-memory read callback and walks records with `DGifGetRecordType`, `DGifGetImageDesc`, `DGifGetLine` and `DGifGetExtension`/`DGifGetExtensionNext` (`DGifExtensionToGCB` for the Graphic Control Extension). `DGifGetImageDesc` appends a `SavedImage` (with a copy of the local colour map) on every image even without slurping, so the demuxer and the decoder free them after each descriptor (`GifFreeSavedImages`, resetting `ImageCount`), and the demuxer refuses an image once `max_frames` frames are indexed, before giflib allocates for it. Giflib reports a bad LZW code size as a failed read, so a read error only counts as truncation when every byte has been consumed.
2. **Probe never expands pixels.** `DemuxGif` indexes each frame (rect, interlace flag, disposal, transparency index, delay) and skips image data with `DGifGetCode`/`DGifGetCodeNext`. It enforces `max_dimension` on the canvas, `max_frames`, `max_total_pixels` on frames × canvas, and `max_duration_ms` on the summed durations, like WebM and WebP. A frame rect is up to 65535 × 65535 whatever the canvas, so the **sum of rect areas** (the pixels the LZW decoder will produce) must also stay within `max_total_pixels`. Rects are not rejected on size alone: the decoder's line buffer is one rect row (≤ 64 KB), rows and columns outside the canvas are decoded and dropped, and nothing is allocated for them.
3. **A decoder driven by the index.** `GifDecoder` (`src/decode/gif_decoder.*`) re-reads the stream sequentially and checks each image descriptor against the index. It owns the RGBA canvas, a buffer for "restore to previous" (sized from the index) and the row buffer. `Reset()` reopens the stream and clears the canvas. After any error it refuses frames until `Reset()`, since the canvas is part-drawn. `Anim` treats GIF like WebP: backward seeks reset and replay within the decode budget. The `stage_` allocation in `Anim::Create` and the decoder choice now key on "any canvas format".
4. **Compositing** (browser semantics, [ADR 0001](0001-sampled-reference-frames.md)):
   - The canvas starts fully transparent `(0, 0, 0, 0)`, and again after `Reset()` (what a loop restart shows).
   - Disposal applies after a frame has been shown, before the next is drawn. 2 ("background") clears the frame's rect to transparent, never to the palette's background colour. 3 ("previous") restores the rect as it was before the frame drew on it (transparent for the first frame). 0 and 1 leave the frame. The values 4–7 are undefined and mean 0.
   - The Graphic Control Extension covers the next image only; one whose length isn't 4 is ignored.
   - The transparency index leaves the canvas pixel unchanged. A local colour map overrides the global one.
   - **A pixel index the palette doesn't have, and every pixel of a frame with no colour map at all, draws nothing**, like the transparency index. (Black was the alternative. It would paint opaque pixels where a browser shows the canvas, and an unmapped index is more likely a file that lost its map than one that wants black.)
   - Interlaced frames are de-interlaced (passes at rows 0/8, 4/8, 2/4 and 1/2).
   - **A rect that extends past the logical screen is clipped to it**, and one wholly outside draws nothing. **A zero-size logical screen** takes its size, per zero dimension, from the far edge of the first frame (`left + width`, `top + height`), and is `WT_ERR_INVALID_DATA` if that is zero too. Later frames clip to it.
   - A frame with a zero-size rect is valid and draws nothing.
5. **Delays.** GIF delays are centiseconds. A delay below 20 ms (0 or 1 cs) plays for 100 ms, as browsers do; everything else is the file's value, so the manifest's durations are exact. Durations are ≥ 1 and pts is the running sum.
6. **`has_alpha`** is true whenever some pixel can end up transparent, decided without reading pixels: any frame declares a transparency index (used or not); the first frame, clipped, doesn't cover the canvas; a frame other than the last uses "background" disposal (the last frame's doesn't show, because a loop restarts on a cleared canvas); the first frame uses "previous" disposal and isn't the last; or a frame has no colour map, or an LZW code size larger than `max(2, log2(palette size))` (so its pixels can name missing entries). Conservative: it can say true for a GIF that never exposes transparency. When false, the output has no alpha plane.
7. **Truncated files.** `giflib` reads sequentially, so no prefix copy is needed: a file that ends before its trailer plays its complete frames with `info.truncated` set (this includes a complete file whose `;` is missing). No complete frame is `WT_ERR_TRUNCATED`. A structural error (unknown record type, LZW code size outside 2–8) is `WT_ERR_INVALID_DATA` whatever precedes it. An LZW error found while decoding is `WT_ERR_DECODE` for that frame; as for WebP, later frames then replay through it, so they fail too until a seek back before it.
8. **A GIF writer for tests** (`native_test/gif_writer.h`) crafts inputs the corpus doesn't have: any rect, disposal, delay, transparency index, palettes, interlace, raw extensions and deliberate damage. `fuzz/gif_seeds.cc` uses it to write `fuzz/corpus/gif/`.
9. `WT_API_VERSION` is unchanged: `wt_probe` and `wt_anim_create` now succeed for GIF. The frame cache needed no change.

## Colour accuracy

Measured against the premultiplied references of `anim_disposal.gif` (6 frames, 96 × 96, checked through the C ABI), the same way as [ADR 0022](0022-animated-webp.md):

| Check | Measured minimum | Bar |
|---|---|---|
| 1:1 colour (sequential and after seeks) | 50.01 dB | 45 dB (shared) |
| 1:1 alpha | identical | identical |
| 48 × 48 bucket (2:1), colour | 50.01 dB | 45 dB (shared) |
| 36 × 36 and 24 × 24 buckets, colour | **15.26 dB** | **14 dB** (GIF-specific; shared: 34) |
| Buckets, alpha | 30.69 dB | 30 dB (shared) |

Unlike WebP, the 1:1 loss is small: the corpus rects sit on even coordinates, so 4:2:0 loses almost nothing. The 2:1 bucket keeps every edge on the pixel grid and is just as good. The 0.375 and 0.25 buckets fall far below the shared colour bar, and it is not a bug in the compositing (alpha is exact at 1:1 and the 1:1 colour is 50 dB). The cache is 4:2:0, so after scaling one chroma sample covers 8 × 8 source pixels at a 4:1 reduction, and the corpus is made of pure saturated colours with pixel-aligned edges. Where such an edge runs between two colours (the magenta stripes against the green checkerboard in frame 3, for instance), the chroma sample mixes them, and the full-resolution luma next to it then contradicts it: a pixel that should be magenta comes out green. Real stickers are smoother, which is why WebM and the WebP corpus clear 34 dB, but a hard-edged GIF drawing hits this at small buckets. Transparent pixels don't cause it (they are black, so scaling straight alpha only darkens a pixel that is part transparent, and an oracle that models that gives the same numbers).

So the colour bar for the non-aligned buckets is GIF-specific (`kGifMinBucketRgbPsnr`), set from the measurement with about 1.2 dB of margin; it still catches a wrong filter, a shift, a flip or a swapped channel, which land lower. The 2:1 bucket keeps the strict bar. Fixing the cause would mean bleeding opaque colour into transparent and chroma-conflicting regions before conversion, which touches the shared `RgbaToYuva` path for every format and is left for a follow-up if real sticker sets show it.

## Consequences

- No new dependency; `src/CMakeLists.txt` already linked `gif`.
- `fuzz_gif` covers the demuxer (index invariants) and the decode path at a small bucket and source size (seeks, skips, tight limits). `fuzz_sniff` no longer expects GIF to be rejected, and `fuzz_probe` takes the GIF seeds.
- The decode budget counts canvases as before. A GIF whose rects are far larger than its canvas can't exceed it, because the rect areas are bounded at probe time.
- A GIF whose LZW stream is damaged in frame *k* fails frame *k* and every later frame until a seek before *k*, like WebP. Resynchronising at the next frame would need a frame offset index.
